## 成员表读写审计（用户要求：「确保创建时所有字段均会填写，或走完该函数所在的工作流后能完成全部字段读写」）

**审计结论**：`members` 的写入只有三个入口（全仓无裸 SQL，都走 `shared/resources.ts` 元数据）：
① 后台通用 CRUD `POST|PUT /api/admin/content/members` → `admin-content.ts` → `repo.ts`；
② 学生邀请函转正 `POST /api/applications/invite/:token` → `applications.ts: confirmInvite`；
③ 演示数据 `seed-content.ts` → `insertSeedEntity`。
读取只有 `listEntities` / `getEntity`（`columnList` = `id` + 全部字段列，`rowToEntity` 全量解码）→ 读侧本来就无遗漏。

**原来的缺口**：
1. `entityToRow` 遇到没提交的 key 直接跳过 → 写不写满整行全看调用方，缺的列靠建表 SQL 的 DEFAULT 兜底；
2. `confirmInvite` 的成员对象**漏了 `destination`**；
3. `direction`（在组）/`destination`（已毕业）这对互斥字段**从来没有被校验**过，两项可以同时为空；
4. `createEntity` 非自增分支返回 `{ id, ...input }` —— **新增接口的返回值不含补上的默认值与时间戳**，与「读」不同形。

**改动**（`npm run typecheck` + 改动文件的 eslint 均通过）：
- `worker/lib/repo.ts`：`createEntity`/`insertSeedEntity` 改成先 `{ ...defaultEntity(def), ...input }` 再 `entityToRow`
  → INSERT 覆盖**全部列**；非自增分支改为**回读整行**返回（复用 `getEntity`），新增接口形状与读一致。
  `updateEntity` **刻意不动**（仍只写提交上来的列，这样部分更新不会把别的字段清空）。
- `shared/resources.ts`：`direction`/`destination` 加 `requiredWhen`（与 `showWhen` 同条件）→ 在组必填负责方向、已毕业必填毕业去向。
- `shared/types.ts`：`Member` 的 `destination`/`avatarUrl`/`sortOrder` 由可选改**必填**（D1 这三列都是 NOT NULL DEFAULT，读出来必然有值，原来的 `?` 是错的）。
- `shared/seed.ts`：种子改用 `SeedMember`（三字段可选）+ `map` 补默认值，导出仍是完整的 `Member[]`。
- `worker/routes/applications.ts`：`confirmInvite` 显式写 `destination: ''`（整行齐全），并新增 `direction` 必填校验（与 requiredWhen 同一条规则）。
- `src/sections/InviteSection.tsx`：负责方向加 `*`、提交前本地校验、加一行提示。
- `src/admin/ContentPage.tsx`：提交前用**同一个** `validateEntity` 先本地校验（不再白跑接口拿 400）；必填星号对 `requiredWhen` 也生效。

**以后照着改的口径**：读 = 全列；创建 = 默认值补全后整行写、并回读整行；更新 = 只写提交的列；
校验 = 唯一 `validateEntity`；互斥字段 = `requiredWhen` + `showWhen` 同条件（已同步进 `MEMORY.md` 的架构约定）。

**顺带**：`MEMORY.md` 超限被截断，按规则整篇重写了一遍（合并招新章节、删掉已作废的场次/自动流程/Cron/时间窗描述）。

## Bug：「方向与身份」页的方向名编辑框打不了字（用户报的）

**现象**：方向名输入框只能敲进一个字符就失焦，中文输入法完全没法用。

**根因**：`MemberRolesPage` 的表格行 `key` 写成了 `` key={`${role.label}-${index}`} `` ——
而 `label` 正是这一行里**正在被编辑的输入值**。敲一个字 → key 变化 → React 认为这是"另一行" →
卸载并重建整行的输入框 → 焦点丢失（输入法合成途中被切断）。**key 用了可编辑的内容，是这个 bug 的全部原因。**

**修法**：给行加一个与内容无关的本地标识 `rowId`（`type EditableRole = MemberRole & { rowId: string }`，
模块级自增计数器生成，不用 `crypto.randomUUID()` —— 后者在非安全上下文（如 http 局域网 IP）不可用），
`key={role.rowId}`；`rowId` **只用于渲染、不参与保存**（`validateMemberRoles` 只读已知字段，天然会丢掉它）。
保存后用服务端规范化结果重建 rows 时，**按位置把本地 rowId 还回去**（提交前 order 已写成 i*10，服务端也按 order 排序，位置能对齐），
否则整表会重建、把编辑中的焦点又弄丢一次。

**教训（值得复用）**：React 列表里只要有一项是**可编辑的输入**，它的 key 就绝不能取自该输入的内容
（label / name / title 都不行），必须用独立 id —— 否则表现为「输入框打不了字」，很容易被误判成受控组件或 IME 的问题。

顺手确认：全 `src/` 已无 `` key={` `` 形式的 key（grep 0 命中）。`tsc -b` + eslint 通过，
`npm run build` 后重跑；`wrangler dev` 是**按请求从 dist 目录读文件**的，所以构建完不用重启服务，刷新页面即可。

## 分析：项目介绍板块「获奖数不等 → 卡片会不会不等长」（未改代码）

用户问的起点：`ProjectsSection` 的卡片在荣誉条数不同时是否会被撑得长短不一。读代码后的结论（未动一行）：

- **数据侧现状**：荣誉是**单个字符串** `honor`（`shared/types.ts:52`），后台字段 `type:'text'`，
  `hint` 已写「可写多项荣誉用「；」分隔」（`shared/resources.ts:234`）—— 也就是**目前还没有「条数」概念**，
  多条只能靠分号塞在一个串里。若要「按项渲染」，先得决定是前端 split 还是改数据结构。
- **布局侧**：`ProjectsSection.tsx:58` 是 `grid gap-6 sm:grid-cols-2`，卡片 `flex flex-col`（:62），
  描述 `flex-1`（:74）吸收剩余空间，荣誉块（:75）与标签行（:81）在描述之后。
- **结论 A：同一行的两张卡片不会不等高** —— CSS Grid 默认 `align-items:stretch`，卡片被拉到整行高度，
  多出来的空间被 `flex-1` 的描述吃掉；行高 = 该行最高卡片的高度。
- **结论 B：不等的是「行与行之间」**（内容驱动的固有差异），以及**同一行内荣誉块的顶边会错位**
  （底部因 flex-1 而对齐）。
- **要避免的写法**：给卡片加 `items-start`/`self-start`/`h-fit` 会取消 stretch，那时同一行也会长短不一。
- **两处口径已经不一致**：首页精选卡片对荣誉用了 `line-clamp-2`（`HomeSection.tsx:137`），项目页完全展开。
- 给用户的三个选项：① 保持单串、前端 `；` split，配 `line-clamp-2` + 「等 N 项」（零迁移，推荐先做）；
  ② 改成 `honors: string[]`（`type:'tags'`）+ 迁移 `0012`（结构化、后台可增删单条，但要动 shared/迁移/两处前台）；
  ③ `grid auto-rows-fr` + `h-full` 让全页等高（留白多，被最长卡片决定）。等用户拍板再动手。
